# Bottle Feed Logger stand, V2

A printed stand for the Bottle Feed Logger: a base that holds the breadboard
and the load cell, a lid with the display window and two buttons, a collar that
hides the load cell, and the pan the bottle sits on. It is a fully parametric
Fusion model, so every size comes from one parameter table and the whole thing
rebuilds from a script.

> **Status: 2.0.0-beta.1.** V2 is verified in CAD but **has not been printed
> yet.** It is derived from V1, which was printed and used. Six measurements
> are still estimates, listed under [What is and is not verified](#what-is-and-is-not-verified).
> Expect a test print to turn up something before 2.0.0.

## Get the files

Printable files are attached to the GitHub release, not kept in the repo:
[releases](https://github.com/pravton/bottle-feed-logger/releases).

| File | What it is |
|---|---|
| `...-base.stl`, `...-lid.stl`, `...-collar.stl`, `...-pan.stl` | One mesh per part, for slicing |
| `...-<part>.3mf` | The same parts as 3MF, where Fusion could export them |
| `...-assembly.step` | The whole stand as solids, for opening in any CAD tool |
| `...manifest.json` | Exactly which version, commit and parameter values made these files |
| `bottle-feeder-v1-reference.zip` | The V1 prototype meshes, for `docs/v1-teardown.md` |

Every file name carries the version, so a loose STL always says what it is.

## Printing

Four parts, all print flat with **no supports**. Each STL comes out in its
assembled orientation, so turn the lid over in the slicer.

| Part | Lay it on the bed | Notes |
|---|---|---|
| Base | Floor down, as exported | Two small bridges over the screw counterbores, both well within normal bridging |
| Lid | **Flip it: top face down** | The ribs and standoffs then point up. The visible face gets the bed finish |
| Collar | Standing on its rim, as exported | An open tube, nothing overhangs |
| Pan | Bottom down, as exported | Turn on **ironing** for the top: it is the surface the bottle sits on |

PLA is fine indoors, PETG if it will see warmth. 0.2 mm layers, at least 3
walls, 30 to 40% infill: rigidity matters, because a flexing part reads as noise.
The lid skin over the hollowed underside is 0.9 mm, which is two to three
perimeters on a 0.4 mm nozzle.

## Hardware

Screw lengths are derived from the geometry, not picked by eye. To regenerate
this table after changing any parameter, run `python3 tests/fasteners.py`.

| Qty | Screw | Length | Where |
|---|---|---|---|
| 4 | M3 button head, ISO 7380 | 14 mm | Lid to base, from underneath. Self-taps into the printed standoffs |
| 2 | M5 socket head, ISO 4762 | 25 mm | Load cell fixed end into the base boss, from underneath |
| 1 | M4 button head, ISO 7380 | 10 mm | Pan onto the load cell free end, through the spacer |
| 1 | Washer, 20 mm OD x 1.5 mm | | Spacer between the load cell and the pan |

The load cell threads (**M5 at the fixed end, M4 at the free end**) are
inferred from V1's counterbores. Check yours before buying screws.

Electronics are in the [main BOM](../../../bom/bill-of-materials.md). The stand
is sized for a half-size breadboard (55 x 84 mm) and two 12 mm capped buttons.

## Assembly

The full sequence is in [`hardware/assembly.md`](../../../hardware/assembly.md).
In short:

1. Screw the load cell's fixed end into the base boss from underneath, arrow
   pointing down. The free end points toward the display end.
2. Fit the breadboard into the base and run the USB cable out through the notch
   in the back wall.
3. Press the collar into the lid opening. A dab of glue stops it working loose.
4. Put the lid on the base and fit the four screws from underneath.
5. Put the spacer washer on the load cell's free end, then the pan, and fit its
   screw.
6. **Check the pan and collar touch nothing.** Any contact between the fixed
   and moving parts is a second load path: the scale will not fail, it will
   quietly read wrong.

## What is and is not verified

**Verified**

- The model builds in Fusion with every sketch fully constrained and no failing
  features.
- All 72 driving parameters are swept to both ends of their range offline,
  and the parts stay coherent at every extreme.
- A stock screw length fits every hole.
- The V1 cutout positions are reproduced to within 0.001 mm.

**Not verified**

- **V2 has never been printed.** Fit, print quality and assembly are untested.
- Six values are still estimates: `bottle_footprint_dia`, `breadboard_h`,
  `component_stack_h`, `load_cell_deflection`, `load_cell_length` and
  `load_cell_span`. The last one sets where the pan sits.
- The free-end thread is inferred, not measured.
- Weighing accuracy, corner loading and the overload stop are untested.
  `docs/design-spec.md` explains why corner loading matters most here.

## Changing the design

### How this works

The model is **generated by a script, then edited in Fusion if you like**.

```
params/*.json          single source of truth for every dimension
      |
      v
src/bundle.py          composes a standalone Fusion script
      |
      v
build/fusion_script.py run it in Fusion (Scripts and Add-Ins)
      |
      v
Fusion document        real User Parameters + real timeline features
```

The script writes Fusion **User Parameters**, not baked numbers. After a build
you can open `Modify > Change Parameters` and drag sizes around, and the
formulas stay live. But the repo is the source of truth: values changed only in
Fusion are overwritten by the next build unless they are copied back into
`params/`.

### The central idea

**Nothing is positioned or sized absolutely if it can be derived.**

V1 hardcoded a 150 x 104 outside *and* a 140.5 x 94 cavity. That
over-constrains the wall, which came out 4.75 mm on two sides and 5.00 mm on the
other two. In V2 the components and the wall are inputs, and the case is
whichever of two requirements governs:

```
cavity_min_l = breadboard_x + boss_l + 3 * clearance_component
footprint_l  = pan_l + 2 * stability_margin_l
case_l       = max(cavity_min_l + 2 * wall, footprint_l)
```

Along the case, stability wins comfortably. Across it the two are almost tied,
so a small change can flip which one sets the width.

Positions are measured inward from a wall, so a feature cannot be driven off the
part. Paired sizes are derived from each other, so a screw head can never end up
wider than the counterbore that takes it:

```
boss_offset_x        = case_l / 2 - wall - boss_end_gap - boss_l / 2
pan_counterbore_dia  = free_screw_head_dia + 2 * fit_slip
pan_plate            = max(pan_plate_min, plate needed to bury the screw head)
```

### Rules

Enforced, not just documented.

- **No magic numbers in geometry.** Every sketch dimension references a named
  parameter, and `validate.py` fails the build on a literal.
- **A small set of driving inputs**; everything else is a formula.
- **Clearances are named and per-process** (`fit_*`), so switching process
  profile re-tunes every fit at once.
- **Every sketch fully constrained.**
- **No feature keyed to auto-numbered faces.** Features reference named
  construction planes. The only exceptions, the edge fillets and chamfers, are
  re-selected geometrically on every build and placed last in the timeline.
- **Every driving parameter has a valid range**, and the model is rebuilt at
  both ends of it.
- **Provenance is tracked**: every parameter is `measured`, `design`,
  `standard`, `inferred` or `placeholder`, and the unmeasured ones are reported
  on every build.

### Checks

From this folder, no Fusion needed, Python 3 only:

```bash
python3 src/bundle.py --no-sweep
python3 tests/test_resolve.py
python3 tests/check_v1_fit.py
python3 tests/test_geometry_mock.py
python3 tests/fasteners.py --check
```

These run in CI on every pull request that touches this folder.

`test_geometry_mock.py` runs the build against a mock Fusion API. It proves the
script runs end to end, that every expression refers to real parameters, and
that the parts are coherent at nominal and at both limits of every driving
parameter. `src/fusion/validate.py` then runs inside Fusion after a real build:
it rebuilds at the limits, checks timeline health and hunts for hardcoded
dimensions. Both matter. The Fusion pass has caught things the mock cannot,
such as a sketch plane whose local axes do not map to world axes the obvious
way.

### Building in Fusion

```bash
python3 src/bundle.py
```

Then in Fusion: `Utilities > Scripts and Add-Ins > Scripts > + > From Device`,
and run `build/fusion_script.py` with a design document open. Add `--export` to
write the release files to `build/export/`, and `--no-sweep` to skip the
in-Fusion range sweep, which takes several minutes.

Rebuilding clears and regenerates the timeline, so the script refuses to run on
a document containing anything it did not create.

## Releasing a new version

1. Change parameters or source in a pull request. CI runs the checks above.
2. Bump `meta.version` in `params/default.json` and add a `CHANGELOG.md` entry.
3. If `python3 tests/fasteners.py` output changed, update the hardware table
   here and the project BOM in the same pull request.
4. After merging, build from a clean checkout with `--export`. The manifest's
   `git_sha` must not end in `-dirty`, or the files cannot be traced back to
   the repo.
5. Tag `stand-vX.Y.Z` and publish a GitHub release with the per-part STLs and
   3MFs, the assembly STEP and the manifest. Mark it a pre-release until the
   version has been printed and assembled.
